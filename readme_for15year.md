# 📘 Понятный гайд по `graph_builder.py` и `core_builder.py`

Представь, что ты строишь **карту знакомств** между словами. Не просто «это слово похоже на то», а «эти два слова встречаются в одних и тех же поисковых запросах». Если люди часто ищут «купить холодильник» и «купить стиральную машину», значит слова «холодильник» и «стиральная машина» связаны через «купить».

Из этой карты потом можно достать **семантическое ядро** — список слов, которые логично группируются вокруг стартового слова (например, вокруг «доставка»).

Ниже — как это работает, по-человечески.

---

## 🗺️ Общая картина: три этапа + сборка ядра

```
keywords.txt (106 ГБ)
   │
   │   ЭТАП 1: SCAN
   │   Читаем файл, оставляем только «хорошие» запросы
   ▼
keywords_ids.bin (6.7 ГБ) — компактный список запросов в виде чисел
   │
   │   ЭТАП 2: LINKS
   │   Для каждого запроса считаем все пары слов внутри него
   ▼
links (таблица в базе) — сколько раз каждая пара встретилась
   │
   │   ЭТАП 3: PRUNE
   │   Выкидываем пары, которые встретились слишком редко
   ▼
Готовый граф (18.9 млн связей между 200k слов)
   │
   │   CORE BUILDER
   │   Идём от стартового слова по связям, набираем ядро
   ▼
core_words.csv — семантическое ядро
```

---

## 🧩 Этап 1: SCAN — «просеиваем запросы»

**Что делает:** читает `keywords.txt` (106 ГБ, 1.9 млрд строк) и оставляет только те запросы, которые стоит учитывать.

**Что на входе:** файл, где каждая строка — `запрос<TAB>показы<TAB>точные показы`.

**Что на выходе:** `keywords_ids.bin` — компактный файл, где каждый запрос превращён в набор чисел (ID слов) + вес.

### Параметры SCAN

| Параметр | Что значит по-простому | Дефолт | Зачем менять |
|---|---|---|---|
| `--min-freq` | Минимальный «вес» запроса (сколько раз его искали). Запросы с весом меньше — выкидываем | `2` | Если хотите больше данных — поставьте `1`. Если меньше шума — `5` или `10` |
| `--max-words` | Сколько максимум слов берём из одного запроса | `8` | Длинные запросы («купить недорого холодильник в москве с доставкой») шумные. 8 — разумно |
| `--query-col` | Какая колонка в файле — сам запрос | `1` (первая) | Если у вас файл другого формата |
| `--freq-col` | Какая колонка — вес | `last` (последняя) | То же |
| `--delim` | Разделитель колонок | авто (`\t`) | Если файл с `;` или `,` — задать вручную |
| `--all-pos` | Разрешить **все** части речи | выкл | По умолчанию берутся только существительные, прилагательные, глаголы и т.д. Если нужны местоимения/предлоги — включить |
| `--allow-latin` | Разрешить латиницу | выкл | По умолчанию только кириллица. Если в запросах есть английские слова — включить |
| `--lemmatize-new` | Лемматизировать незнакомые слова (приводить к начальной форме) | выкл | Если в данных много слов, которых нет в словаре — включить |
| `--restart` | Начать **с нуля** (удалить всё, что было) | выкл | Если хотите пересчитать после смены `--min-freq` |

**Что важно понять:**
- **`--min-freq` — самый важный параметр.** Он определяет, сколько данных останется. При `--min-freq 2` проходит 10.6% строк (205 млн из 1.9 млрд). При `--min-freq 1` прошло бы ~40–50%.
- **Менять `--min-freq` после скана нельзя** — только `--restart` (пересчёт с нуля, +1ч15м).

## 🔗 Этап 2: LINKS — «считаем, кто с кем дружит»

**Что делает:** читает `keywords_ids.bin`, для каждого запроса берёт все пары слов внутри него и считает, сколько раз каждая пара встретилась.

**Пример:**
```
Запрос «купить холодильник» (вес 100)
  → пара (купить, холодильник): count += 100, hits += 1

Запрос «купить стиральную машину» (вес 50)
  → пара (купить, стиральная): count += 50, hits += 1
  → пара (купить, машина): count += 50, hits += 1
  → пара (стиральная, машина): count += 50, hits += 1
```

**Что на выходе:** таблица `links` в базе. Каждая строка — `(слово1, слово2, суммарный вес, число разных запросов)`.

- **`count`** — суммарный вес (сколько всего показов у всех запросов с этой парой).
- **`hits`** — DF пары (в скольких **разных** запросах встретилась пара). Это важнее для качества.

### Параметры LINKS

| Параметр | Что значит по-простому | Дефолт | Зачем менять |
|---|---|---|---|
| `--top-lemmas` | Брать только N самых частых слов (по DF). Остальные — игнорировать | `0` (все) | **Главный параметр этапа.** Меньше N → меньше граф, быстрее. Больше N → полнее, но дольше |
| `--min-lemma-hits` | Альтернатива `--top-lemmas`: брать слова, у которых DF ≥ N | `0` (выкл) | Если хотите «все слова с DF ≥ 10» вместо «топ-200k» |
| `--all-lemmas` | Разрешить строить граф по **всем** словам | выкл | ⚠️ **Опасно:** миллиарды пар, десятки часов, база 50–100 ГБ. Только если реально нужно |
| `--links-restart` | Начать связи **с нуля** (очистить `links`) | выкл | Если меняете словарь (`--top-lemmas`) или пороги — обязательно |
| `--links-buffer` | Сколько пар держать в памяти перед записью в базу (млн) | `3.0` | Больше → меньше коммитов, быстрее, но больше RAM |
| `--no-prune` | Не отсекать после построения | выкл | **Рекомендую всегда:** сначала построить полный граф, потом посмотреть `--df-hist`, потом отсечь |

**Что важно понять:**
- **`--top-lemmas 200000`** — оптимально для вашего случая. Это точка, где 99.4% всех пар сохраняются. Дальше — почти не растёт.
- **`--all-lemmas`** — почти никогда не нужен. 200k слов покрывают почти всё.
- **`--no-prune`** — всегда ставьте при первом построении. Prune необратим, лучше сначала посмотреть.

## ✂️ Этап 3: PRUNE — «выкидываем случайные связи»

**Что делает:** удаляет из `links` пары, которые встретились слишком редко. Пара, которая была в 1–2 запросах, скорее всего случайна. Пара, которая была в 10+ запросах — устойчивая.

**Что на входе:** таблица `links` (49 млн рёбер).

**Что на выходе:** отфильтрованная `links` (18.9 млн рёбер при `--min-pair-hits 5`).

### Параметры PRUNE

| Параметр | Что значит по-простому | Дефолт | Зачем менять |
|---|---|---|---|
| `--min-pair-hits` | Минимальный DF пары. Пары с `hits < N` удаляются | `3` | **Главный параметр.** `5` — баланс. `10` — компактнее, но теряет специфику. `3` — шире, но больше шума |
| `--min-pair` | Минимальный `count` (суммарный вес) | `0` (выкл) | Доп. фильтр по весу. Обычно не нужен |
| `--top-edges` | Оставить только N самых сильных связей у каждого слова | `0` (выкл) | Если граф слишком плотный — можно ограничить |
| `--vacuum` | Сжать файл базы после удаления | выкл | **Рекомендую:** 12 ГБ → 3.1 ГБ. Занимает 4–5 минут |

**Что важно понять:**
- **Prune необратим.** Понизить порог потом можно только через `--links-restart` (+1ч48м).
- **Повысить порог** можно в любой момент — просто ещё раз `--prune-only --min-pair-hits 10`.
- **`--vacuum`** — не обязателен, но сильно экономит место.

### Как выбрать `--min-pair-hits`

Смотрите на `--df-hist`:

```
DF >= 3:  26.1 млн рёбер (796 МБ)
DF >= 5:  18.9 млн рёбер (576 МБ)   ← рекомендую
DF >= 10: 11.8 млн рёбер (360 МБ)
DF >= 20:  7.1 млн рёбер (218 МБ)
```

**Правило:** берите порог, где число рёбер **5–20 млн**. Меньше 5 млн — слишком агрессивно (потеря специфики). Больше 20 млн — много шума.

## 🔍 Вспомогательные команды (не этапы)

| Команда | Что делает | Когда использовать |
|---|---|---|
| `--dry-run` | Пробный прогон на выборке: показывает воронку фильтров, прогноз размера, топ неизвестных слов | **До** скана. Понять, что данные вообще пройдут фильтры |
| `--report` | По готовому ID-файлу оценивает, сколько будет рёбер при разных `--top-lemmas` | **После** скана. Подобрать `--top-lemmas` |
| `--df-hist` | Показывает распределение DF пар в `links` | **После** links. Подобрать `--min-pair-hits` |
| `--status` | Быстрый статус: что где лежит, на каком этапе | В любой момент. Проверить, что всё на месте |
| `--scan-only` | Остановиться после скана | Если хотите сделать scan, а links — потом |
| `--prune-only` | Только отсечь (без links) | После `--df-hist` |
| `--links-only` | Только связи (без скана) | После скана или `--report` |

## 🧠 `core_builder.py` — сборка семантического ядра

**Что делает:** берёт стартовое слово и идёт по графу, набирая слова, которые «логично рядом». Итеративно: на каждом шаге выбирает лучшего кандидата из соседей текущего ядра.

**Аналогия:** вы в незнакомом городе. У вас есть карта знакомств (граф). Вы начинаете с одного человека (стартовое слово). Спрашиваете: «кто знает его?» — получаете список. Выбираете самого «связанного» (у кого больше общих друзей с ядром). Добавляете в ядро. Повторяете.

**Что на входе:**
- `data/input/start_words.txt` — стартовые слова (по одному на строку).
- `data/output/semantics.db` — готовый граф.
- `config/core_builder.yaml` — настройки.

**Что на выходе:** `data/output/core_words.csv` — таблица слов ядра с метаданными.

### Параметры `core_builder` (в YAML)

| Параметр | Что значит по-простому | Дефолт | Зачем менять |
|---|---|---|---|
| `min_connections` | Минимум связей кандидата с ядром. Если у слова только 1 связь с ядром — это случайность | `1` | Поднять до `2` — ядро будет «плотнее», но меньше |
| `max_connections` | Максимум связей. Слова-«хабы» (у которых связи со всем) могут зашумить ядро | `null` (выкл) | Поставить `50` — отсечь «попсу» |
| `min_word_freq` | Минимальная частота слова в корпусе | `0` | Поднять до `100` — убрать редкие слова |
| `max_word_freq` | Максимальная частота. Слишком частые слова («купить», «цена») — не специфичны | `null` (выкл) | Поставить `1_000_000` — отсечь «попсу» |
| `min_link_weight` | Минимальный вес ребра, чтобы сосед попал в кандидаты | `0` | В графе уже prune по DF ≥ 5, так что `0` — нормально |
| `max_core_size` | Сколько слов набрать в ядро | `200` | Для первого прогона — `100`. Потом можно больше |
| `mark_dicts.enabled` | Помечать слова из `dict/*.txt` | `true` | Если у вас есть словари — включить. Слова **не исключаются**, а помечаются |
| `mark_groups.enabled` | Помечать слова из групп БД | `true` | Если таблица `groups` пуста — выключить |
| `checkpoint.enabled` | Сохранять промежуточный результат | `true` | Оставить включённым |
| `checkpoint.interval` | Как часто сохранять (каждые N итераций) | `10` | — |
| `output.format` | Формат вывода: `csv`, `txt`, `both` | `csv` | `txt` — только список слов. `csv` — с метаданными |
| `output.include_all` | Включать ли отсеянных кандидатов в CSV | `true` | Удобно для отладки — видно, кого отсеяли и почему |
| `output.show_marks` | Показывать колонку «метки» | `true` | — |

### Как работает выбор кандидата (упрощённо)

На каждом шаге для каждого кандидата считается **score**:

```
score = (сумма весов связей с ядром − самая сильная связь) / частота слова
```

**Почему так:**
- **Сумма весов** — чем больше связей с ядром, тем лучше.
- **Минус самая сильная связь** — защита от «одной очень сильной связи», которая может быть случайной.
- **Деление на частоту** — штраф за «попсовые» слова. «Купить» связано со всем, но не специфично.

Кандидат с самым высоким score добавляется в ядро. Повтор.

## ⚠️ Три правила, которые спасут от боли

1. **Не меняйте `--min-freq` после скана.** Это пересчёт с нуля (+1ч15м). Решайте до.
2. **Не запускайте `--prune-only` вслепую.** Сначала `--df-hist`, посмотрите цифры, выберите порог.
3. **Не запускайте `--all-lemmas` без крайней необходимости.** 200k слов покрывают 99.4% пар. Полный граф — 50–100 ГБ и десятки часов.

## 🚀 Быстрый старт: что делать прямо сейчас

1. **Создайте `data/input/start_words.txt`:**
   ```
   купить
   доставка
   ```

2. **Создайте `config/core_builder.yaml`:**
   ```yaml
   core_builder:
     min_connections: 2
     max_core_size: 100
     mark_dicts:
       enabled: true
       use_all: true
     mark_groups:
       enabled: false
     checkpoint:
       enabled: true
       interval: 10
     output:
       format: "csv"
       include_all: true
       show_marks: true
   ```

3. **Запустите:**
   ```bash
   python scripts/core_builder.py
   ```

4. **Откройте `data/output/core_words.csv`** и посмотрите, что получилось.

Если ядро маленькое (< 20 слов) — уменьшите `min_connections` до `1`. Если в ядре «мусор» — увеличьте `min_connections` до `3` или добавьте `max_connections: 50`.
